# PixelForge — ТЗ (Junior+ Docker Compose)

## Идея

Сервис обработки изображений. Пользователь загружает картинку через веб-форму →
API сохраняет оригинал на диск и создаёт запись в PostgreSQL со статусом `pending` →
отдельный **воркер** забирает задачи из очереди прямо в PostgreSQL (без Redis — это
осознанное решение, чтобы попрактиковать паттерн "очередь на базе БД" через
`SELECT ... FOR UPDATE SKIP LOCKED`), генерирует превью 200×200 и ч/б версию через
`sharp`, обновляет статус на `done`. Nginx отдаёт статику фронтенда, проксирует
`/api/*` на API и напрямую отдаёт файлы (оригиналы и обработанные) из shared volume.

## Архитектура — ровно 4 контейнера

1. **nginx** — реверс-прокси + статика фронтенда + отдача файлов из volume
2. **api** — Node.js/Express, REST API
3. **worker** — Node.js, фоновый обработчик очереди (`sharp`)
4. **postgres** — БД: таблица `images` = данные + очередь задач в одном месте

## Что уже готово (мой код, лежит в архиве)

- `frontend/` — простая HTML/CSS/JS форма загрузки + список картинок
- `nginx/nginx.conf` — рабочий конфиг (3 location-блока: статика, proxy, alias)
- `api/` — исходники Express API (upload, list, get by id)
- `worker/` — исходник поллинг-воркера с `sharp`
- `db/init.sql` — схема таблицы `images`
- `.env.example` — список нужных переменных окружения

Код рабочий как Node.js-приложение сам по себе (можно запустить `npm install && npm start`
локально с поднятым Postgres, чтобы проверить логику до докеризации).

## Что нужно сделать тебе (Docker-часть)

- `Dockerfile` для `api` — multi-stage, `node:20-alpine` в финальном слое, non-root user
- `Dockerfile` для `worker` — multi-stage; **осторожно с `sharp`**: это нативная библиотека
  с C-биндингами (`libvips`). Prebuilt-бинарник собирается под конкретную платформу —
  на `alpine` (musl) он не всегда подхватывается автоматически, как на `debian` (glibc).
  Придётся разобраться, что произойдёт при `npm install` на alpine, и решить: доставать
  нужный бинарник вручную, переключиться на `node:20-slim`, или собирать из исходников.
  Это специально заложенная junior+ ловушка.
- `docker-compose.yml`:
  - именованная сеть
  - именованные volumes: `pg-data`, `uploads`, `processed`
  - `uploads` и `processed` должны быть смонтированы одновременно в `api`, `worker` и `nginx`
    по одинаковым путям (см. `.env.example`: `UPLOAD_DIR`, `PROCESSED_DIR`)
  - `env_file` для всех сервисов (как обычно у тебя — без `${VAR}`-интерполяции)
  - `healthcheck` для `postgres` (`pg_isready`)
  - `depends_on: condition: service_healthy` для `api` и `worker` относительно `postgres`
  - `db/init.sql` подключить через volume в `/docker-entrypoint-initdb.d`
- `.dockerignore` для `api/` и `worker/` (`node_modules`, `.env`, `.git`)

## Как обычно, перед Dockerfile — три вопроса

Для каждого сервиса:
1. без каких библиотек код не запустится (для `worker` — это в первую очередь `sharp`,
   и он тянет за собой нативный бинарник, а не просто JS-пакет)
2. где лежит главный исполняемый файл (`src/index.js` в обоих сервисах)
3. нужны ли сервису внешние файлы (да: `UPLOAD_DIR`/`PROCESSED_DIR` — не часть образа,
   должны приходить через volume)

## Критерии готовности

- `docker compose up -d --build` поднимает все 4 сервиса без ошибок
- Полный цикл работает: загрузка через фронт → воркер обрабатывает → превью и ч/б
  версия доступны по прямой ссылке через nginx
- Все Dockerfile — multi-stage, все процессы внутри контейнеров — не под root
- `postgres` имеет healthcheck, `api`/`worker` реально дожидаются его готовности
  (можно проверить: `docker compose up` и посмотреть порядок логов)
- Итоговые образы разумного размера — без dev-зависимостей в финальном слое
